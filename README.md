Technical Risk Treatment Report: GRC103 Risk Assessment & Management TechniquesOrganization: Northbridge ServicesRole: GRC Analyst and Technical Control ImplementerTarget Environment: Local Ubuntu Server 24.04 LTS (Isolated Network) & Kali Linux (Auditor/Testing Node)Date: November 8, 20261. Executive SummaryAs the GRC analyst and technical control implementer for Northbridge Services, a technical risk treatment assessment and hands-on hardening campaign were executed on our local internal document server running Ubuntu Server 24.04 LTS. The primary objective was to address legacy exposures, unrestrictive document directories, and network access vulnerabilities without interrupting the approved internal web portal (/public/).Through this project, preventive, detective, and corrective controls were successfully implemented, validated, and documented using a Kali Linux testing node. Baseline evaluations indicated critical vulnerabilities, including an unauthenticated legacy service running on port 8080, open directory listings exposing dummy records, and unsegmented network access. Following the implementation of service retirement, directory restrictions, UFW firewall controls, and backup/restoration validation, the organization's overall risk profile was substantially lowered. This report outlines our technical findings, risk register transitions, four-strategy risk treatments (Avoidance, Mitigation, Transfer, and Acceptance), cost-benefit analyses, and ongoing operational monitoring requirements.2. Technical Risk Treatment ImplementationStep 1: Applying Avoidance to the Legacy Workflow (R1)To address R1, the unnecessary legacy service was retired via service termination and disabling, eliminating the attack surface on port 8080 while keeping the approved port 80 service intact.Proposed Change: Retire unused legacy Python HTTP server endpoint (grc-legacy.service).Business Impact: Zero impact on approved business operations; removes extraneous code and listening ports.Approval Role: GRC Change Control Board (Simulated).Rollback Procedure: sudo systemctl enable --now grc-legacy.Execution Commands & Verification:Bashsudo systemctl disable --now grc-legacy
sudo systemctl is-active grc-legacy
sudo ss -lntp
Post-Treatment Validation: Nmap scans from Kali confirmed port 8080 was closed/filtered, while port 80 remained fully accessible. This avoids the retired workflow's exposure but does not eliminate risks inherent to the remaining active web service.Step 2: Implementing Preventive Controls — Removing Archive Publication (R2)To resolve R2, the archive folder was relocated outside the web root, file permissions were restricted to root only, and Nginx configurations were updated to disable autoindex and explicitly deny access to the old path.Execution Commands:Bashsudo mkdir -p /srv/grc-private
sudo mv /var/www/grc-lab/archive /srv/grc-private/
sudo chmod -R go-rwx /srv/grc-private/
Nginx Configuration Update (/etc/nginx/sites-available/grc-lab):Nginxserver {
    listen 80;
    server_name _;
    root /var/www/grc-lab;
    access_log /var/log/nginx/grc_access.log combined;
    error_log /var/log/nginx/grc_error.log;

    location / {
        autoindex off;
    }
    location /archive/ {
        deny all;
    }
}
Validation: Testing from Kali confirmed that /public/ returned HTTP 200, whereas /archive/ and direct requests to /archive/dummy-records.txt returned HTTP 403 Forbidden. Note that disabling directory listings alone prevents browsing, but explicit access denial (deny all) or moving files outside the web root is required to prevent direct-file retrieval if filenames are guessed.Step 3: Restricting Network Access with UFW (R3)To mitigate network-layer exposure (R3), Ubuntu's Uncomplicated Firewall (UFW) was configured to enforce a default-deny inbound posture, allowing traffic to port 80 exclusively from the authorized Kali testing IP (192.168.56.10).Execution Commands on Ubuntu:Bashsudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow from 192.168.56.10 to any port 80 proto tcp
sudo ufw logging on
sudo ufw enable
sudo ufw status numbered
Blocked-Source Verification Test from Kali:Bashsudo ip addr add 192.168.56.11/24 dev eth0
curl --interface 192.168.56.11 --connect-timeout 5 "http://192.168.56.20/public/"
sudo ip addr del 192.168.56.11/24 dev eth0
Result: Unapproved source 192.168.56.11 experienced a connection timeout and failed to reach the web portal. UFW logging confirmed drops on incoming packets from unauthorized IPs.Step 4: Verification of Detection and Recovery (R4)Log CorrelationRequests from the approved Kali address to /public/ and /archive/ were correlated against Ubuntu system logs:Nginx access logs recorded successful HTTP 200 requests for /public/ and HTTP 403 responses for /archive/.Kernel / UFW logs (sudo journalctl -k / /var/log/ufw.log) recorded explicit [UFW BLOCK] events for unauthorized probing from secondary test interfaces, proving that firewall-blocked traffic was dropped at the network layer before reaching the Nginx application layer.Backup and Verified Restoration ExerciseTo establish resilience against data loss (R4), a secure local backup workflow was tested:Created a restricted backup directory (/srv/grc-backups, permissions 700).Generated a tarball archive and SHA-256 integrity hash of the original portal:Bashsudo tar -czpf /srv/grc-backups/public-before-test.tgz -C /var/www/grc-lab public
sha256sum /var/www/grc-lab/public/index.html | tee ~/portal-before.sha256
Simulating data loss, the index file was removed (sudo rm /var/www/grc-lab/public/index.html), confirming service failure from Kali.Performed restoration:Bashsudo tar -xzpf /srv/grc-backups/public-before-test.tgz -C /var/www/grc-lab
sha256sum -c ~/portal-before.sha256
Outcome: Hash verification succeeded (OK), and Kali re-verification confirmed HTTP 200 with original content restored. Observed recovery time was under 60 seconds. Note: While local same-host backups validate restoration mechanics, they do not protect against total host hardware failure or hypervisor compromise.5.
